🛡️ 開支索償與收支管理系統
系統架構、資安防禦與安心使用白皮書

致全體團隊成員與夥伴：
為了讓大家在進行日常開支報銷、單據核對與財務管理時更加高效、透明且享有最高規格的隱私保障，我們正式啟用了本套專屬管理系統。本文件旨在公開系統的底層架構、前後端防禦邏輯及隱私隔離機制。

🏛️ 一、 基礎設施：Google Firebase 全球企業級雲端服務

本系統並非架設於隨時面臨單點故障或漏洞風險的傳統主機，而是完全基於 Google Cloud Platform (GCP) 旗下的 Google Firebase 伺服器端無伺服器（Serverless）架構，具備與跨國金融機構同等級別的安全標準：

  • 傳輸層安全協議（TLS 1.3 / HTTPS 256-bit 加密）： 所有客戶端與雲端伺服器之間的通訊均受全鏈路高強度加密保護，徹底杜絕中間人攻擊（MITM）與封包嗅探。
  • 密碼學身分鑑別（Firebase Authentication & JWT）： 使用者每次登入，Google 會簽發一張具備時效性且帶有密碼學數位簽章的 JSON Web Token (JWT)。每一次操作皆由 Google Auth 進行身分校驗，無法透過偽造 Cookie 或 Session 冒名頂替。
  • 分散式高可用資料庫（Cloud Firestore）： 資料具備多資料中心異地即時備份與強一致性保證，具備 99.999% 服務可用性，無遺失數據風險。
  • 二進位儲存槽與存取控制（Firebase Cloud Storage）： 收據發票圖片獨立存放於物件儲存槽（Blob Storage），並由底層安全性規則直接進行存取控制列表（ACL）管控。

🔒 二、 專屬邀請暗號機制（封閉式團體專用門禁）

為了確保系統純淨運作，完全隔離公網爬蟲與未授權人員，系統實施了嚴密的門禁機制：

  • 非公開註冊模式： 系統全面關閉公開註冊。新成員必須取得由管理員親自發放的專屬暗號（區分大小寫，具備密碼學複雜度），方能完成帳號初始化。
  • 防暴力窮舉與防拖庫（Anti-Enumeration）： 在伺服器端 Firestore Rules 中，徹底關閉了客戶端批量讀取權限。外部或惡意腳本無法透過 API 一鍵抓取所有暗號清單；客戶端僅能以 get 進行單筆精準比對，只要大小寫或字元不符即刻拒絕。
  • 配額鎖定與原子計數： 每個邀請暗號均設有使用次數上限（Limit）與使用紀錄（Audit Log），額滿自動失效，杜絕暗號被無限轉發。

🛡️ 三、 前後端防禦縱深：面對惡意「F12 開發者工具」時的防禦邏輯

許多具備 IT 知識的朋友會關心：「網頁客戶端代碼在瀏覽器皆可檢視，若有惡意使用者透過 F12 / Postman / DevTools 篡改 API 或腳本，系統能防得住嗎？」

本系統採用「前端主動消毒 + 服務端零信任（Zero-Trust Server-Side Enforcement）」的雙層架構，所有安全性檢驗均在 Google 伺服器端完成，前端的任何篡改皆無法突破防線：

【防禦審計對照表 (Server-Side Enforcement)】 【攻擊者客戶端嘗試 (F12 / API)】 【Google 伺服器端規則審計】 【結果】 1. 傳送 payload 將 role 改為 'admin' ──➔ 檢查: request.resource.data.role == 'member' ──➔ ❌ 403 拒絕提權 2. 發起 Update 請求修改單據金額 ──────➔ 檢查: allow update: if isSuperAdmin() ──➔ ❌ 403 禁止修改 3. 嘗試讀取非本人 UID 的收據圖檔 ────➔ 檢查: request.auth.uid == userId ──➔ ❌ 403 阻斷讀取 4. 在輸入欄位夾帶 XSS 惡意腳本 ────────➔ 前端: escapeHtml() 轉義為純文字實體編碼 ──➔ 🛡️ 腳本失效

1. 垂直提權防禦（Privilege Escalation Protection）

情境：攻擊者在註冊或更新時，透過 Console 控制台將 role 欄位強行寫入 "admin"。

防禦：Firestore 規則強制限定註冊時 request.resource.data.role == 'member'。任何非管理員試圖賦予自身 Admin 權限的請求，將在資料庫層級直接被阻斷並拋出 Permission Denied。

2. 帳目防篡改機制（Immutable Financial Ledger）

情境：單據提交後，使用者試圖透過 Postman 發送 update 請求調高報銷金額或修改匯率。

防禦：一般會員在伺服器端完全沒有任何修改權限（allow update: if isSuperAdmin()）。單據一旦建立，其金額、幣別、匯率與分類在物理層面上即成為永久唯讀狀態。

3. 發票圖片 UID 物理目錄隔離（Row-Level Storage Security）

情境：使用者試圖透過猜測或遍歷檔名，下載或刪除其他成員的敏感發票收據。

防禦：所有單據圖片均存放在 /claims/{userId}/{fileName} 目錄下。Storage 規則在每次存取時嚴格校驗 request.auth.uid == userId。非該檔案擁有者（或管理員），Google 伺服器在通訊協定層直接回絕，連 1 個 Byte 的資料都不會外洩。

4. 單據生命週期與審核鎖定（Status-Based Deletion Lock）

未審核階段（Unclaimed）：若填寫有誤，會員擁有自主刪除權限（resource.data.status == 'unclaimed'），可自由撤回並重新提交。

已入帳階段（Claimed）：一旦管理員審批通過，單據狀態轉為 claimed，系統策略自動撤銷一般會員的刪除權限，防止任何一方事後湮滅財務憑證。

5. XSS 跨站腳本與重複提交防護

前端消毒：所有渲染至 DOM 的動態資料均經過 escapeHtml() 轉義處理，有效防範 HTML/JS 注入攻擊。

防重複點擊（Debounce / Disable）：提交及登入按鈕於發送請求瞬間立即處於 disabled 狀態，防止網路波動導致重複寫入。

📋 四、 全體成員安心承諾清單

核心關切事項 系統技術保障機制 安全狀態
我的收據隱私會外洩給其他會員嗎？ 由 Firebase Storage 依據用戶專屬 UID 進行物理隔離，僅本人及審查管理員有權讀取。 🔒 絕對不會
已提交的帳目會被他人暗中修改嗎？ 一般會員無資料庫 Update 權限，單據金額具備不可篡改性（Immutability）。 🔒 絕對不會
若填寫錯誤或上傳錯檔案該如何處理？ 審核前可自由撤回。在管理員審批入帳前，您可以隨時自行刪除單據並重新提交。 🔒 審核前可撤回
單據審核通過後的安全性？ 審核鎖定機制。標記入帳後即鎖定為正式歷史檔案，會員無法刪除，確保雙方權益。 🔒 雙方權益鎖定
系統具備防範惡意攻擊的能力嗎？ 架構於 Google Firebase 企業級雲端之上，所有安全檢驗皆於伺服器端強制執行，前端 F12 竄改完全無效。 🔒 極高防護力

索取專屬邀請暗號

向管理員索取邀請代碼（例如：VIP-Pass88，請務必注意英文大小寫）。

開始報帳
