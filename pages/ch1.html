🔒 一、 點解註冊一定要有「專屬邀請暗號」？（封閉式團體門禁）

我哋呢個系統係絕對不對外公開嘅內部天地，所以設有嚴密的「熟人守門機制」：

  1. 非公開註冊模式（拒絕陌生人隨便入嚟）：
    系統唔開放畀公眾註冊。只有收到管理員親手發放嘅專屬暗號（區分大小寫，例如 VIP-Pass88），先可以成功完成帳號初始化。
  2. 伺服器端防拖庫（Anti-Enumeration，黑客撞唔到、偷唔走）：
    暗號鎖喺雲端保險箱。在伺服器端 Firestore Rules 中，徹底關閉咗客戶端批量讀取權限（allow list: if isSuperAdmin()）。外部黑客或惡意腳本完全無辦法一鍵抓取暗號清單；客戶端只能進行單筆精準比對，只要大小寫或字元唔符即刻拒絕！
  3. 配額鎖定與原子計數（用完即止，杜絕無限轉發）：
    每個邀請暗號均設有使用次數上限（Limit）與 Audit Log 使用紀錄，額滿自動失效，杜絕暗號被私下無限轉發。
💡 Firebase 原廠安全系統核心精要：
  • Firebase Auth 絕對認證 Token：每次登入均由 Google 發放具備密碼學數位簽章的 JWT，杜絕 Session 偽造。
  • Cloud Firestore Rules 嚴格審計：資料庫實施「零信任」權限隔離，非授權請求會在 Google 伺服器端第一時間被拒絕。
  • Anti-Enumeration & 防撞防爬機制：關閉所有清單查詢列舉（List），杜絕暴力破解與腳本爬蟲。
  • App Check 原廠防護：綁定合法設備指紋，阻斷所有來自非法腳本或未授權 App 端的惡意 API 請求。

🛡️ 二、 就算有人按「F12 開發者工具」搞破壞，都完全無效！（前後端雙重鐵壁）

許多具備 IT 知識嘅朋友會關心：「網頁客戶端代碼喺瀏覽器按 F12 皆可檢視，如果有人透過 Console 控制台、Postman 或腳本竄改代碼，會唔會偷睇到嘢或者報假帳？」

答案係：完全唔會！ 我哋採用咗「前端消毒 + 服務端零信任 (Zero-Trust Enforcement)」嘅雙層架構，所有安全性檢驗均喺 Google 伺服器端完成，前端按 F12 進行任何竄改皆無法突破防線：

【防禦審計對照表 (Server-Side Enforcement)】 【攻擊者客戶端嘗試 (按 F12 / API 腳本)】 【Google 伺服器端規則審計】 【結果】 1. 傳送 payload 將 role 改為 'admin' ──➔ 檢查: request.resource.data.role == 'member' ──➔ ❌ 403 拒絕提權 2. 發起 Update 請求修改單據金額 ──────➔ 檢查: allow update: if isSuperAdmin() ──➔ ❌ 403 禁止修改 3. 嘗試讀取非本人 UID 的收據圖檔 ────➔ 檢查: request.auth.uid == userId ──➔ ❌ 403 阻斷讀取 4. 在輸入欄位夾帶 XSS 惡意腳本 ────────➔ 前端: escapeHtml() 轉義為純文字實體編碼 ──➔ 🛡️ 腳本失效

❌ 嘗試 1：想按 F12 / API 繞過介面偷睇其他人的收據相片？

Google 伺服器審計： 檢查 request.auth.uid == userId。

防禦結果： ❌ 403 阻斷讀取！ 每位會員都有一個獨立的專屬私密資料夾（/claims/{userId}/{fileName}）。伺服器只會認你本人嘅登入憑證，非該檔案擁有者（或管理員），Google 伺服器直接回絕，連 1 個 Byte 嘅資料都偷睇唔到。

❌ 嘗試 2：想按 F12 構造 Update 封包事後改大金額？

Google 伺服器審計： 檢查 allow update: if isSuperAdmin()。

防禦結果： ❌ 403 禁止修改！ 一般會員喺伺服器端完全沒有任何修改權限。單據一旦建立，金額、幣別與匯率喺物理層面上即成為永久唯讀狀態（Immutable Ledger），杜絕改單報假帳。

❌ 嘗試 3：想按 F12 發送腳本把自己升級做「管理員 Admin」？

Google 伺服器審計： 檢查 request.resource.data.role == 'member'。

防禦結果： ❌ 403 拒絕提權！ 註冊與更新權限由伺服器端死死鎖定為一般會員，任憑前端點樣改，伺服器一律拒絕垂直提權（Privilege Escalation）。

💡 填錯嘢想修改點算？（單據生命週期與審核鎖定）
• 未審核階段（Unclaimed）： 只要管理員仲未批核入帳（status == 'unclaimed'），你可以隨時自行刪除填錯嘅單據再重新交過，非常彈性！
• 已入帳階段（Claimed）： 一旦管理員審核轉為 claimed，系統處理邏輯自動撤銷一般會員嘅刪除權限，鎖定為正式財務歷史存檔，保障雙方誠信與權利！

❌ 嘗試 4：想喺輸入欄位夾帶 XSS 惡意代碼？

前端消毒： 所有渲染至網頁嘅文字均經過 escapeHtml() 轉義處理，惡意腳本完全無法運行。

防重複提交： 按鈕於發送請求瞬間自動啟用 Disable 狀態，防止網絡波動導致重複寫入。

☁️ 三、 後台靠山：Google Firebase 國際企業級雲端服務

我哋嘅系統並非架設於隨時面臨單點故障嘅傳統主機，而是直接運行喺 Google 旗下嘅企業級 Serverless 雲端架構 —— Firebase，具備與跨國金融機構同等級別嘅安全標準：

  • Google 級傳輸加密（TLS 1.3 / HTTPS 256-bit）：
    全站採用軍規加密，客戶端與雲端伺服器之間嘅通訊受全鏈路保護，徹底杜絕中間人攻擊（MITM）與封包嗅探。
  • 密碼學身分鑑別（Firebase Authentication & JWT）：
    每次大家登入，Google 會自動發出一張具備時效性且帶有密碼學數位簽章嘅 JSON Web Token (JWT)。每一次操作都經由 Google Auth 進行身分校驗，絕無人可以偽造 Cookie 冒名頂替。
  • 發票獨立保險箱（Firebase Cloud Storage & Firestore）：
    資料具備多資料中心異地即時備份（99.999% 高可用性）。收據圖片獨立存放於物件儲存槽（Blob Storage），配合每個人嘅 UID 獨立隔離，只有你自己同審核管理員睇得到。
🛡️ APPCHECK 設備指紋小提示：
系統已整合 Google Firebase App Check 原廠資安認證機制（配合 reCAPTCHA v3 / DeviceCheck）。系統會自動驗證發出請求的是否為「經過 Google 認證的合法前端 App/瀏覽器」，徹底拒絕所有未經授權的外部自動化腳本、模擬器或 Bot 攻擊，防護規格直逼金融級應用！

⚙️ 附錄：Google Firebase 原廠強大功能與自定後端邏輯架構

本系統結合 Google Firebase 原廠強大基礎設施 與 自訂後端零信任防禦邏輯，建構出完整資安閉環：

  1. 雲端原生安全架構（Firebase Cloud Native Security）
    • Atomic Counters（原子操作計數）：邀請碼扣減與計數採用 Server-Side 原子操作，防止併發請求（Race Conditions）造成的超額漏洞。
    • Granular ACL（細粒度存取控制）：Firebase Storage 安全規則基於 JWT Claims（request.auth.token）動態驗證，實行 Row-Level Security 檔案隔離。
  2. 自訂後端商業邏輯（Custom Server-Side Business Logic）
    • Role-Based Access Control (RBAC)：嚴格劃分 member 與 admin 角色。權限由資料庫 Document 與 Custom Claims 強制雙重鎖定。
    • Immutable State Transition（狀態機不可逆鎖定）：單據狀態自 unclaimed 轉換至 claimed 後，由後端規則阻斷刪除與變更指令，確保財務 Audit Trail（審計追蹤）完整性。
  3. App Check 與防爬蟲生態系（Bot Defense & Integrity）
    • Device Integrity Verification：結合 App Check 機制，防範中間人偽造 API 封包，確保每一次資料寫入皆來自驗證合格的正版前端介面。
