Chapter 2 ・ 進階資安剖析

超越 F12：Web 潛在破解途徑
與 Google Firebase 深度防禦分析

超越前端工具的資安視野：
以網路安全與系統架構的角度來看，「F12 開發者工具」只是前端（瀏覽器端）的檢視與測試工具，並不是唯一的攻擊路徑。
在真實世界中，黑客或資安人員如果要評估或挑戰一個 Web 應用程式，通常會從傳輸層、身分鑑別層、API 介面、依賴套件等多個維度尋找潛在漏洞。
由於本系統採用了 Google Firebase 企業級 Serverless 架構，許多傳統伺服器的漏洞（例如 SQL 注入、伺服器作業系統漏洞）已由 Google 團隊底層防護。本章節將深度剖析除了 F12 以外的 5 大潛在破解維度及其對應防禦機制。

🎯 一、 繞過前端，直接對 API 發起請求（API Bypassing）

潛在攻擊手法：繞過 UI 邏輯構造 HTTP 封包 威脅等級：高

攻擊者不需要使用瀏覽器的 F12 介面，而是利用 Postman、cURL 或自訂的 Python / Node.js 腳本，完全繞過前端 UI 介面的任何限制（例如前端輸入框的位數限制或按鈕禁用的 JavaScript 邏輯），直接將數據封包發送給 Firestore 或 Storage API。

🛡️ 系統深度防禦機制：
  • 伺服器端強制執行規則（Firestore Rules）：後端寫得非常嚴謹，Security Rules 在伺服器端實施了 allow update: if isSuperAdmin() 與 request.resource.data.role == 'member'。
  • 防禦結果：代表任何繞過前端 UI 構造的惡意 API 請求，都會在 Google 伺服器端第一時間被拒絕並拋出 Permission Denied。

🔑 二、 認證與 Token 竊取 / 洩漏（Auth & Session Hijacking）

潛在攻擊手法：獲取合法使用者的身分憑證 威脅等級：高

攻擊者不攻擊資料庫本身，而是嘗試獲取合法使用者的身分憑證（JWT Token / LocalStorage Session），進而冒用身分操作：

  1. 跨站腳本攻擊 (XSS)：如果網站允許使用者輸入未經轉義的 HTML/JavaScript 程式碼，惡意腳本在其他人的瀏覽器執行時，就能讀取 localStorage 內的認證資料。
  2. 憑證釣魚 (Phishing) 或弱密碼暴力破解：嘗試猜測使用者的密碼（若使用者設定了弱密碼）。
  3. 中間人攻擊 (MITM)：在未加密的公共 Wi-Fi 中截取傳輸封包。
🛡️ 系統深度防禦機制：
  • 全站 TLS 1.3 (HTTPS) 高強度加密：杜絕網路傳輸過程中的封包截取。
  • 前端動態字串消毒（XSS Sanitization）：全面使用 escapeHtml() 處理所有動態渲染文字，阻斷 XSS 腳本執行。
  • Firebase Authentication 憑證託管：採用具備密碼學數位簽章的 JWT Token，並支援高強度密碼驗證。

💣 三、 邀請碼自動化窮舉（Brute-Force & Enumeration）

潛在攻擊手法：自動化腳本碰撞邀請暗號 威脅等級：中

如果邀請暗號過於簡單（例如 123 或 2026），攻擊者可以撰寫自動化腳本，以極高的速度向 Firebase 發起註冊請求，試圖「撞出」正確的邀請碼來非法開戶。

🛡️ 系統深度防禦機制：
  • 暗號高複雜度要求：邀請碼要求具備一定長度與英文大小寫混合（例如 VIP-Pass88）。
  • Cloud Firestore 權限限縮：徹底關閉 allow list: 批量查詢權限，不給攻擊者一次過扒光暗號清單的機會。
  • App Check & Rate Limiting：整合 Google Firebase App Check（配合 reCAPTCHA v3），阻斷自動化 Bot 腳本頻繁請求。

📦 四、 前端第三方函式庫供應鏈漏洞（Supply Chain Vulnerability）

潛在攻擊手法：利用第三方 CDN 舊套件漏洞 威脅等級：中

前端引入了幾項常見的第三方 CDN 函式庫（例如 xlsx.full.min.js、jszip.min.js、FileSaver.min.js）。如果 CDN 連結被污染，或引入了帶有已知 CVE 漏洞的舊版本函式庫，攻擊者可能利用解析特製的檔案引發記憶體溢出或 XSS 攻擊。

🛡️ 系統深度防禦機制：
  • 官方可信 CDN 引用：嚴格限定使用官方可信之 CDN 來源（如 cdnjs）。
  • 版本維護與 SRI 哈希驗證：定期更新 CDN SDK 至穩定防護版本，必要時加入 Subresource Integrity (SRI) 雜湊值校驗，確保程式碼未遭竄改。

🚨 五、 邏輯漏洞與資產濫用（Denial of Service / Storage Exhaustion）

潛在攻擊手法：合規帳號上傳巨量檔案耗盡資源 威脅等級：中

攻擊者註冊成為合法會員後，利用合法的權限，持續、大量上傳 9.9MB 的垃圾圖片，試圖塞爆 Storage 儲存空間或拉高 Firebase 雲端帳單成本。

🛡️ 系統深度防禦機制：
  • Storage Rules 格式與大小限制：限制單檔大小於 10MB 內，且檔案類型必須嚴格為圖片格式（image/*）。
  • GCP 預算告警與配額管理：設定 GCP Budget Alerts 告警機制，極端情況下可配合 Cloud Functions 限制單一 UID 每月上傳張數上限。

🏛️ 六、 結論：資安縱深防禦（Defense in Depth）架構

資安核心哲學：
在資安縱深防禦的架構下，「網頁原始碼或 F12 被人看光」並不可怕。
真正的資安核心在於：即便攻擊者拿到完全公開的前端程式碼、甚至直接發送 API 封包，Google 伺服器端的權限規則（Firestore Rules + Storage Rules + App Check）依然能牢牢鎖死第一線！
只要後端的 Security Rules 邏輯無懈可擊，本系統對於一般及進階攻擊者來說皆具備了極高的防護壁壘。
